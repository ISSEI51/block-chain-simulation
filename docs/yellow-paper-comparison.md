# Ethereum Yellow Paper との対応

本実装は、ブロックチェーンの基本構造を Ethereum の概念と対応づけながら **大幅に簡略化して** 実装したものです。Ethereum の再実装ではありません。この文書では、どの部分が Yellow Paper（以下 YP）のどの概念に対応し、どこが異なるかを整理します。

## 0. 前提

- YP は Ethereum の **実行層**（トランザクションの実行と状態の更新）の形式的な仕様です。改訂（London、Paris、Shanghai など）ごとに版が更新されており、版によってフィールドや式番号が異なります。この文書では記号を YP の表記に合わせ、式番号は示しません。
- 2022年9月の The Merge（Paris）以降、Ethereum の合意形成は Proof of Stake です。その仕様は YP ではなく、consensus layer の仕様（consensus-specs）で定義されています。
- 本文中の KEC は YP における Keccak-256、RLP は YP の Appendix B で定義されるシリアライズ方式を表します。

## 1. 対応表（概要）

| 本実装 | YP の概念 | 関係 |
|---|---|---|
| `Transaction` | トランザクション T | 構造の対応のみ。中身は大きく異なる（第2節） |
| `transaction_id` | トランザクションハッシュ（KEC で計算） | 内容のハッシュで識別する点は同じ |
| `Block` | ブロック B = (B_H, B_T, B_U, …) | ヘッダと本体の分離は同じ考え方 |
| `index` | ブロック番号 H_i | 同じ（前ブロック + 1） |
| `timestamp` | H_s | YP は秒単位で、親より厳密に大きい必要がある。本実装はミリ秒単位で、親以上であればよい |
| `previous_hash` | 親ブロックのハッシュ H_p | 同じ |
| `transactions_hash` | transactionsRoot H_t | YP は Merkle Patricia Trie の根。本実装は一覧全体の単純な SHA-256 |
| `nonce` | H_n（PoW 時代） | 同じ役割。The Merge 以降、H_n は 0 に固定 |
| `difficulty`（先頭の 0 の個数 d） | H_d（PoW 時代） | 定義が異なる。おおよそ H_d ≈ 16^d に相当（第6節）。The Merge 以降、H_d は 0 に固定 |
| `hash` | ブロックハッシュ KEC(RLP(H)) | ヘッダのハッシュである点は同じ。ハッシュ関数とシリアライズ方式が異なる |
| `Blockchain` が保持する状態 | ワールドステート σ | **厳密には異なる**（第3節） |
| `add_block` / `mine_pending_transactions` | ブロック単位の状態遷移関数 Π | 簡略化したモデル（第4節） |
| `pending_transactions` | トランザクションプール（mempool） | YP では定義されない、クライアント実装の概念 |
| `canonical_json` | RLP | 決定論的なシリアライズである点は同じ |
| SHA-256 | Keccak-256（KEC） | 別のハッシュ関数（第5節） |
| 先頭0個数による PoW | Ethash（〜2022年9月）→ Proof of Stake | 第6節 |
| Genesis Block | Genesis Block | 採掘せず、仕様で決めた固定値をとる点は同じ |

## 2. Transaction ↔ T

| YP のトランザクションの主なフィールド | 本実装 |
|---|---|
| nonce T_n（送信者アカウントがこれまでに送ったトランザクション数） | なし（このためリプレイを防げない） |
| gasPrice T_p、または maxFeePerGas / maxPriorityFeePerGas（London 以降の型） | なし（手数料の概念がない） |
| gasLimit T_g | なし |
| to T_t（受信者アドレス。コントラクト作成時は空） | `recipient`（任意の文字列） |
| value T_v（送金する Wei の量） | なし（送金を扱わない） |
| data T_d / init T_i（呼び出しの入力データ、またはコントラクトの初期化コード） | `payload`（任意の JSON）がおおよそ T_d に相当する |
| 署名 (v, r, s) または yParity | なし |
| （送信者フィールドはない。署名から関数 S(T) で復元する） | `sender`（自己申告の文字列） |
| （タイムスタンプはない。時刻はブロックの H_s が持つ） | `timestamp` |

最も大きな違いは **署名がないこと** です。YP のトランザクションには送信者のフィールドがなく、送信者のアドレスは secp256k1 楕円曲線上の ECDSA 署名から復元されます。そのため、他人になりすましたトランザクションは作れません。本実装の `sender` は自己申告なので、誰でも任意の送信者を名乗れます。

YP には "nonce" が2種類ある点にも注意が必要です。トランザクションの nonce T_n はアカウントごとの通し番号で、ブロックヘッダの nonce H_n は PoW で探索する値です。本実装の `nonce` は後者だけに対応します。

## 3. Blockchain の状態 ↔ σ（厳密には異なる）

**YP のワールドステート σ** は、アドレス（160ビット）からアカウント状態への対応です。アカウント状態は次の4つからなります。

- nonce σ[a]_n
- 残高 σ[a]_b
- ストレージの根 σ[a]_s
- コードのハッシュ σ[a]_c

σ は Merkle Patricia Trie として保持され、ブロックヘッダにはその根のハッシュ（stateRoot H_r）だけが入ります。σ はトランザクションを適用した **結果** であり、ブロックの列そのものではありません。

**本実装の `Blockchain` が保持するもの** は、ブロックの列（履歴）、未承認トランザクション、次の difficulty です。トランザクションを適用した結果として変化する状態（残高やコントラクトの記憶領域）は存在しません。

したがって、本実装の「チェーンの状態」は σ ではなく、YP でいえば **ブロックチェーンそのもの（履歴）** に近いものです。YP の枠組みに当てはめると、本実装は「トランザクションが状態を何も変えず、記録されるだけ」の特殊な場合にあたります。

## 4. ブロック追加 ↔ 状態遷移の簡略モデル

YP は Ethereum を状態遷移系として記述します。

```text
σ_{t+1} ≡ Υ(σ_t, T)        （トランザクション1件による状態遷移）
σ'      ≡ Π(σ, B)          （ブロック1つによる状態遷移）
```

Π は、ブロック内のトランザクションに Υ を順に適用し、最後にブロック単位の処理 Ω（PoW 時代はマイナーへの報酬、Shanghai 以降は引き出しの処理など）を行います。

本実装では、状態 = チェーン C（ブロックの列）とみなすと、ブロック追加は次の **追記のみの状態遷移** として書けます。

```text
C' = C ∥ (B)     ただし V(B, last(C)) が真のとき（偽なら拒否し、C は変わらない）
```

V は `validate_block` の検証規則です（index の連続、previous_hash の一致、ハッシュの再計算、PoW 条件など。[architecture.md](architecture.md) 第5節）。未承認トランザクションの追加も P' = P ∥ (T) という追記です。

YP との主な違い:

- **Υ がない**: トランザクションは記録されるだけで、何の状態も変えません。そのため「トランザクションが有効か」は、内容とIDの整合性だけで判断しています。YP は署名、nonce、残高、gas を確認します。
- **分岐がない**: YP では、ブロックは親を指す木構造をなし、どの枝を正規のチェーンとするかはフォーク選択の規則で決まります。本実装のチェーンは1本の列で、分岐を扱いません。

## 5. SHA-256 と Keccak-256 の違い

| | SHA-256（本実装） | Keccak-256（Ethereum の KEC） |
|---|---|---|
| 系列 | SHA-2（NIST FIPS 180-4） | Keccak（SHA-3 コンテストの採用アルゴリズム） |
| 構造 | Merkle–Damgård 構造 | スポンジ構造 |
| 出力長 | 256 ビット | 256 ビット |
| 伸長攻撃（length extension） | 構造上、成立する | 成立しない |
| Python 標準ライブラリ | `hashlib.sha256` | **なし**（外部ライブラリが必要） |

注意点: Ethereum の Keccak-256 は、のちに NIST が標準化した **SHA3-256（FIPS 202）とはパディングが異なり、同じ入力でも出力が異なります**。Python の `hashlib.sha3_256` は SHA3-256 であり、Ethereum の KEC ではありません。空のバイト列に対する出力で比べると次のとおりです。

| 関数 | 空のバイト列のハッシュ |
|---|---|
| SHA-256 | `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` |
| SHA3-256（`hashlib.sha3_256`） | `a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a` |
| Keccak-256（Ethereum の KEC） | `c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470` |

（3つとも計算して確認済み。SHA-256 と SHA3-256 は Python の `hashlib`、Keccak-256 は外部ライブラリ pycryptodome を使用。Keccak-256 の値は、Ethereum でコードを持たないアカウントの codeHash と同じ値）

本実装で SHA-256 を使ってよい理由: ブロックチェーンの構造が依存しているのは、決定論的であること、入力が少し変わると出力が大きく変わること、原像やコリジョンを現実的な計算量で見つけられないこと、の3つの性質です。これらは SHA-256 と Keccak-256 の両方が満たすため、ハッシュ関数を取り替えてもハッシュによる連結や改ざん検出の仕組みは変わりません。なお、Bitcoin の PoW では SHA-256（を2回適用したもの）が使われています。

## 6. Proof of Work と Ethereum の PoS の違い

### 6.1 本実装の PoW と Ethereum の旧 PoW（Ethash）

| | 本実装 | Ethereum（The Merge 以前、Ethash） |
|---|---|---|
| 条件 | SHA-256 の先頭に d 個の `0` | n ≤ 2^256 / H_d（n は Ethash の出力） |
| 難易度の刻み | 16倍ずつ（d が整数のため） | 連続的に調整できる |
| 難易度の決め方 | 利用者が設定 | 親ブロックとのタイムスタンプ差から毎ブロック自動調整し、ブロック間隔を十数秒に保つ |
| ハッシュ関数 | SHA-256（計算量のみ） | Ethash（数GBのデータセットを読む、メモリ律速の設計） |
| 正規のチェーン | 分岐を扱わない | 累積難易度（total difficulty）が最大のチェーン |

両者の条件は同じ形にそろえられます。本実装の条件「先頭に d 個の 0」は「ハッシュ値 < 2^(256−4d) = 2^256 / 16^d」と同値なので、**YP の H_d に相当するのは 16^d** です。YP の条件 n ≤ 2^256 / H_d の下で、1回あたりの成功確率は約 1/H_d です。したがって H_d は「1ブロックの採掘に必要なハッシュ計算回数の期待値」という物理的な意味を持ちます。実験1は、この期待値 16^d を実測で確かめるものです。

### 6.2 現在の Ethereum（Proof of Stake）

The Merge（2022年9月15日）以降、Ethereum は PoS で動いています。

- ETH を預け入れた（ステークした）バリデータの中から、12秒ごとのスロットごとに、ブロック提案者が擬似乱数（RANDAO）で選ばれます。
- 他のバリデータがブロックに投票（attestation）し、フォーク選択（LMD-GHOST）とファイナリティ（Casper FFG）が決まります。ファイナライズされたブロックを覆すには、全ステークの1/3以上が没収（スラッシング）の対象となる違反が必要です。
- YP の実行層ヘッダでは H_d = 0、H_n = 0 に固定され、mixHash の位置には prevRandao（H_a）が入ります。

| | PoW（本実装・旧 Ethereum） | PoS（現在の Ethereum） |
|---|---|---|
| ブロックを作る権利 | ハッシュ計算に最初に成功した者 | 擬似乱数で選ばれたバリデータ |
| 消費する資源 | 計算（電力） | 預け入れた資本（不正をすると没収される） |
| ブロック間隔 | 確率的（指数分布。実験1の考察を参照） | 12秒のスロット単位 |
| ファイナリティ | 確率的（後続ブロックが増えるほど覆りにくくなる） | 経済的ファイナリティ（Casper FFG） |

本実装が PoW を採用したのは、ハッシュ関数と確率の関係を、単一の計算機上の数値実験で直接観察できるためです。PoS の本質は多数のバリデータの間の投票と合意にあるため、P2P ネットワークを持たない本実装の範囲外です。

## 7. その他の簡略化

| 項目 | Ethereum | 本実装 |
|---|---|---|
| シリアライズ | RLP（実行層）、SSZ（合意層） | キーを辞書順に並べた JSON |
| 状態・レシートの格納 | Merkle Patricia Trie（stateRoot、receiptsRoot） | なし |
| トランザクションの格納 | Trie の根 H_t。個々のトランザクションの包含証明ができる | 一覧全体の SHA-256。包含証明はできない |
| アカウント・残高・gas | あり | なし |
| 仮想機械（EVM）・ログ・Bloom フィルタ | あり | なし |
| ommer（uncle）ブロック | PoW 時代にあり | なし |
| ブロック報酬・引き出し | あり（Ω で処理） | なし |
| ネットワーク・フォーク選択 | あり | なし（1台の計算機上の1本のチェーン） |

## 8. 論文中での表現について

誤解を避けるため、次のような表現を推奨します。

- 推奨する表現: 「ブロックチェーンの基本構造（ハッシュによる連結、PoW、改ざん検出）を、Ethereum Yellow Paper の概念と対応づけながら簡略化して実装した」
- 避ける表現: 「Ethereum を実装した」「Ethereum のブロックを再現した」
